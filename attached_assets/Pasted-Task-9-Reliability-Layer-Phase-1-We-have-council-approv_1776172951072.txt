Task 9 — Reliability Layer (Phase 1)

We have council approval to proceed.

This phase must be built in this order:

1. Battery + Signal Awareness
2. Confidence Status
3. ETA + Delay Detection (LIMITED SCOPE)

---

# 🎯 OBJECTIVE

Help the watcher understand:

* Is the phone okay?
* Can I trust the current update?
* Is the person on track?

WITHOUT causing unnecessary anxiety.

---

# PART 1 — BATTERY + SIGNAL AWARENESS

## Build first

Add battery and connection data into the heartbeat/reliability pipeline.

### Add to client heartbeat payload when available:

* `batt` → battery level (0–1 or percentage)
* `chg` → charging state
* `net` → network type/status (`wifi`, `cell`, `offline`, `unknown`)

If a value is unavailable on the current platform, omit it safely.

### Store server-side:

* latest battery level
* charging status
* latest connection/network status
* timestamp of last update

### Watcher-facing examples:

* “Phone online, battery okay”
* “Phone online, battery low (12%)”
* “Phone offline since 4:32 PM”
* “Phone is on, but connection looks weak”

---

# PART 2 — CONFIDENCE STATUS

## Build second

Create an INTERNAL confidence model using inputs like:

* heartbeat freshness
* location freshness
* GPS accuracy
* battery level
* network status

Use internal scoring/logic if useful, BUT do NOT show numbers to users.

### User-facing output must be plain language, not technical

Avoid:

* “We’re less confident”

Prefer:

* “Everything looks reliable”
* “Updates may be delayed right now”
* “Phone is online, but location is less clear”
* “Phone may be offline”

### Suggested bands:

* Strong
* Limited
* Low

These can be internal labels or subtle UI indicators, but the visible text must stay human and calm.

---

# PART 3 — ETA + DELAY DETECTION (V1 SCOPE ONLY)

## IMPORTANT: limited scope

Do NOT do full commute prediction yet.

### Only support ETA for:

* active Safe Walk / Safe Ride
* explicitly active trips

Do NOT yet infer ETA for passive Home/Work commutes.

### Watcher-facing examples:

* “About 14 minutes away”
* “Still on the way”
* “Running a little later than expected”

### Tone rule:

Delays must sound like normal life, not danger.

Avoid:

* “Should have arrived by now”

Prefer:

* “Running a little later than expected”
* “Still on the way”

### Guardrails:

* no constant route polling
* refresh only on meaningful movement / trip progress
* stop ETA once arrived
* conservative thresholds only

---

# PRODUCT RULES

## 1. No anxiety language

Battery, signal, confidence, and ETA must sound calm and helpful.

## 2. No clutter

If you add reliability/context text, keep cards readable.

## 3. No fake precision

If ETA is uncertain, say “about 15 minutes,” not exact countdowns.

## 4. No unsupported assumptions

Do not guess destinations for normal commuting yet.
