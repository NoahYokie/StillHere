  Re: SMS / Alert Abuse Phase 1 — In-App Channel and deliveryFailed

  Good catch on in-app messaging.

  I agree that in-app must be included, otherwise the outbound ledger is incomplete.

  Decision 1 — in_app channel

  Approved.

  Add:

  in_app

  to outbound_channel.

  Log in-app system alerts in outbound_send_log.

  Use the same Category-B dedupe rule for in-app system alerts.

  Do not cap in-app sends in Phase 1.

  Reason:
  It has no third-party provider cost and is an important fallback channel for online Safety Circle members.

  Fallback order approved:

  For SMS capped:
  in_app → push → email

  For Call capped:
  in_app → push → email, and SMS only if SMS is not also capped and the flow expects SMS fallback

  For Email capped:
  in_app → push

  For Push failure:
  in_app still counts as a useful delivered channel if it succeeded

  Decision 2 — deliveryFailed boolean

  I agree in principle, but I want to narrow it.

  Add:

  incidents.deliveryFailed boolean default false

  But only set deliveryFailed=true if ALL attempted channels for a real safety alert fail or are circuit-broken.

  That means:

  SMS failed or circuit-broken
  Call failed or circuit-broken where applicable
  Email failed or circuit-broken where applicable
  Push failed where attempted
  in_app failed where attempted

  Do NOT set deliveryFailed=true just because one provider failed.
  Do NOT set deliveryFailed=true for dedupe.
  Do NOT set deliveryFailed=true while fallback channels are still being attempted.
  Do NOT show scary UI copy automatically in Phase 1 unless the existing UI already has a safe place for it.

  For Phase 1:
  It is acceptable to store deliveryFailed but not prominently surface it yet.

  If surfaced, wording must be restrained:

  StillHere could not confirm delivery through available channels.

  Do not say:
  Emergency failed.
  Help failed.
  Nobody was contacted.
  You are not protected.

  Decision 3 — degradedDelivery

  Approved as already agreed.

  Set degradedDelivery=true when any important provider channel is delayed, capped, or failed, but at least one fallback path is
  still being attempted or likely available.

  Watcher/user copy:

  Some delivery channels may be delayed. StillHere is trying available channels.
