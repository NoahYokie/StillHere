 To: Replit Agent

  Re: SMS / Alert Abuse Audit — Policy Direction

  Good audit. I agree with the core model:

  Category A:
  non-urgent sends should be strictly rate-limited and fail closed.

  Category B:
  real safety sends must remain resilient and should not be weakened.

  I also agree that we need a durable outbound_send_log table.

  However, I want to narrow the first implementation pass to reduce regression risk.

  The goal is to stop SMS/call abuse without destabilizing SOS, missed check-in, Safe Walk, Safety Timer, Drive Safety, and
  wellness escalation.

  Decisions on your five questions:

  1. Category-A per-IP layer

  Yes, add IP-keyed limits on top of user limits for abuse-prone non-urgent routes.

  Apply to:

  family_invite
  resend_invite
  test_broadcast
  contact_test
  drill

  This protects against credential-stuffed accounts and bot abuse.

  But do not use IP limits for real safety alerts.

  2. In-memory caches retire-or-keep

  Agree with your proposal:

  Keep:

  sosInFlightByUser
  recentSosByUser

  Reason:
  The 60-second anti-double-tap lock is useful and low risk.

  Replace durable equivalents for:

  familyInviteSmsCache
  notification-engine COOLDOWN_MS where practical

  But do this carefully.

  If replacing notification-engine cooldown touches too many paths, keep the existing in-memory cooldown and add durable
  outbound_send_log dedupe alongside it for now.

  Do not remove working safety cooldowns until the durable replacement is verified.

  3. Drill cap

  Approved:

  2 per hour
  5 per 24 hours
  1 per destination per 30 minutes

  Also make dry-run/drill SMS clearly say it is a test.

  Do not let dry runs look like real SOS.

  4. degradedDelivery UI surface

  Use the incident detail / watcher card.

  If a Category-B send hits the global provider ceiling, show a restrained warning:

  Some delivery channels may be delayed. StillHere is trying available channels.

  Do not scare the user.
  Do not block the incident.
  Do not say delivery failed unless every channel failed.

  5. Voice extraction

  Do NOT extract all voice handling into a new voice.ts in the first pass unless it is required for the limiter.

  Voice code is high-risk because it is part of real safety escalation.

  Preferred first-pass approach:

  Add a small wrapper around existing client.calls.create call sites, or a local enforceSendPolicy call before those calls.

  Only extract server/voice.ts if you can do it with minimal changes and no behavior drift.

  Build scope I recommend

  Phase 1 should include:

  A. New outbound_send_log table

  Fields:

  id
  userId nullable
  incidentId nullable
  channel: sms | call | email | push
  purpose
  destinationHash
  destinationLast4 nullable
  status
  providerMessageId nullable
  errorCode nullable
  createdAt

  Indexes:

  (userId, purpose, createdAt)
  (destinationHash, purpose, createdAt)
  (incidentId, channel, destinationHash)
  (channel, createdAt)

  Hash destination using server secret, preferably HMAC-SHA256 with SESSION_SECRET or a new OUTBOUND_LOG_SECRET if available.

  Do not store raw phone numbers or raw email addresses.

  B. Policy helper

  Create:

  server/outbound-policy.ts

  Functions:

  enforceSendPolicy(...)
  recordSendAttempt(...)
  markSendProviderResult(...)
  hashDestination(...)

  C. Purpose-aware sendSms

  Add purpose metadata to sendSms and direct SMS call sites first.

  Priority routes:

  family_invite
  resend_invite
  test_broadcast
  contact_test
  drill
  sos
  missed_checkin
  safe_walk
  safety_timer
  drive_crash
  wellness_call
  recovery

  D. Non-urgent route limits

  Implement durable 429 behavior for:

  POST /api/family/invite
  POST /api/test
  POST /api/contacts/test/:id
  POST /api/safety-circle/drill if present
  resend invite / checkin resend if SMS-sending and non-urgent

  Friendly 429 response:

  {
    "error": "rate_limited",
    "retryAfterSeconds": number,
    "friendly": "Please wait before sending another invite."
  }

  E. Real safety dedupe

  Add per-incident dedupe using outbound_send_log:

  same incident
  same contact
  same channel
  same purpose

  Prevent repeated duplicate sends from cron restarts or worker loops.

  Do not block first send for real safety.

  F. Global provider ceilings

  Add env-configurable ceilings:

  MAX_OUTBOUND_SMS_PER_HOUR
  MAX_OUTBOUND_CALLS_PER_HOUR
  MAX_OUTBOUND_EMAILS_PER_HOUR

  Defaults:

  development: disabled or very high
  production fallback if env missing: conservative but not dangerous

  I need your recommendation here before final approval:
  Should production fail open or fail closed if these env vars are missing?

  My preference:
  For Category A, missing ceiling can default to 500 SMS/hour.
  For Category B, missing ceiling should not block real safety sends. It should log a warning and continue.

  G. Push and email

  Do not over-refactor push/email in Phase 1.

  If easy, record them in outbound_send_log.

  But the highest cost and abuse risk is SMS and voice, so prioritize those.

  H. No feature reduction rule

  Do not reduce:

  SOS
  missed check-in escalation
  Safe Walk escalation
  Safety Timer escalation
  Drive crash alerts
  wellness-call urgent help
  contact escalation order
  push/email fallback
  existing incident state transitions

  2. Whether you will use SESSION_SECRET or new OUTBOUND_LOG_SECRET for destination HMAC.
  3. Exact non-urgent limits implemented in Phase 1.
  4. Exact real-safety dedupe rule.
  5. What happens if MAX_OUTBOUND_* env vars are missing in production.
  6. Which direct Twilio voice call sites will be wrapped in Phase 1.
  7. Whether push/email will be logged only, or gated too.
  8. How you will verify that SOS still sends normally after this change.
  9. Whether db:push is required.
  10. Any route you recommend leaving for Phase 2.

  No code changes yet.

  Simple explanation for you:

  Replit’s plan is good, but it is big.

  I’m telling them to focus first on the risky and expensive things:

  - family invite SMS
  - test SMS
  - contact test SMS
  - drill SMS
  - outbound SMS abuse
  - outbound call abuse
  - duplicate safety alerts caused by loops

  But I do not want them to heavily refactor every push/email/call system in one go, because that could accidentally affect safety
  features.

  The rule is:

  - Non-urgent messages get strict limits.
  - Real safety alerts stay strong.
  - Real safety alerts get duplicate protection, not heavy blocking.
  - If SMS is capped, the app should still try other channels.
  - No raw phone numbers should be stored in the new log table. Use hashed destinations.
