  Answers:

  1. HMAC secret choice

  Approved.

  Use OUTBOUND_LOG_SECRET.

  Production should fail closed at boot if OUTBOUND_LOG_SECRET is missing.

  Dev can derive from SESSION_SECRET with a warning.

  2. degradedDelivery boolean

  Approved, but with one condition.

  Add:

  incidents.degradedDelivery boolean default false

  Use it only when a real safety alert hit a provider ceiling or severe provider send failure.

  Do not set it for ordinary dedupe.

  Do not show scary copy.

  Watcher copy should be restrained:

  Some delivery channels may be delayed. StillHere is trying available channels.

  3. Category-B 5-minute dedupe window

  Mostly approved, but adjust the rule.

  Current proposed rule:

  same incidentId, channel, destinationHash, purpose within 5 minutes

  This is fine for duplicate-loop prevention.

  But I want one safety exception:

  If the app is intentionally escalating to the same contact through the same channel as part of a later escalation step, or a
  manual retry after visible failure, it must be allowed.

  So use this rule:

  Deduplicate Category-B sends only when:
  same incidentId
  same channel
  same destinationHash
  same purpose
  same escalationStep or null escalationStep
  status IN queued/sent/delivered
  createdAt > now - 5 minutes

  This means we need either:

  A. Add escalationStep nullable integer/text to outbound_send_log

  or

  B. Include a dedupeKey text field that encodes purpose + incident + step + channel + destination

  My preference:
  Add dedupeKey text nullable.

  For most sends:
  dedupeKey = `${incidentId}:${purpose}:${channel}:${destinationHash}`

  For escalation steps:
  dedupeKey = `${incidentId}:${purpose}:${step}:${channel}:${destinationHash}`

  For manual retry:
  dedupeKey should include retry id or retry timestamp bucket so it is not blocked by an older attempt.

  Reason:
  We want to stop accidental duplicate loops, not block intentional escalation or retry behavior.

  4. drive_crash exemption

  Do not fully exempt drive_crash from dedupe.

  Instead:

  First crash/SOS send always allowed.
  Further crash sends for the same incident/contact/channel/purpose should be deduped unless a new incident is created.

  Reason:
  A possible crash flow is safety-critical, but also high-risk for repeated sensor loops.

  5. Category-B circuit breaker behavior

  Need a wording correction.

  You wrote:

  Category B never blocked. Log critical, status='circuit_broken', continue with channel fallback.

  Important distinction:

  If SMS ceiling is hit, do not send SMS past the ceiling.

  That channel is circuit-broken.

  But do not block the incident and do not block other channels.

  So the behavior should be:

  Category B SMS over SMS ceiling:
  do not send that SMS
  record circuit_broken
  try push/email/call fallback where appropriate
  set incident.degradedDelivery=true

  Category B call over call ceiling:
  do not place that call
  record circuit_broken
  try SMS/push/email fallback where appropriate
  set degradedDelivery=true

  This protects cost/provider abuse while keeping safety flow alive.
