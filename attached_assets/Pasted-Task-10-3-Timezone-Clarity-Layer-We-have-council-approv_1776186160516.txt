Task 10.3 — Timezone Clarity Layer

We have council approval to proceed.

This is a trust feature, not just formatting.

Goal:
Make times clear and intuitive when the protected user and watcher are in different places.

---

# 🎯 OBJECTIVE

Ensure:

* check-in scheduling follows the protected user’s local timezone
* watcher-facing times are shown in the watcher’s local time
* dual-time context appears only when it actually helps

---

# CORE RULES

## 1. UTC ONLY IN DATABASE

All timestamps must remain stored in UTC.
Do not store local-time strings in DB.

Examples:

* created_at
* checkin_due_at
* last_heartbeat_at
* incident timestamps
* report/timeline timestamps

---

## 2. PROTECTED USER TIMEZONE = SCHEDULING ANCHOR

Add/support a user timezone field using IANA format, for example:

* Australia/Perth
* Australia/Melbourne
* Europe/London

This timezone must control:

* check-in scheduling
* “next check-in” logic
* any daily/weekly scheduled behavior

The user’s safety schedule follows **their** timezone, not the server timezone and not the watcher timezone.

---

## 3. WATCHER TIME = DISPLAY MIRROR

Watcher-facing surfaces should display time in the watcher’s current local timezone by default.

This applies to:

* watcher dashboard
* watcher timeline
* watcher safety report
* watcher notifications where relevant

---

## 4. DUAL-TIME ONLY WHEN TIMEZONES DIFFER

If watcher timezone == user timezone:

* just show the time normally
* no extra labels

If watcher timezone != user timezone:

* watcher local time is primary
* user local time appears in detail view only

Example:

* “Confirmed safe at 6:31 PM your time (4:31 PM in Perth)”

Do NOT show:

* UTC offsets
* timezone abbreviations like AWST/UTC+8
  Use human place labels instead.

---

## 5. TIMEZONE DIFFERENCE SHOULD NOT CLUTTER MAIN UI

Do NOT put dual-time on:

* collapsed cards
* routine push copy unless necessary

Use dual-time in:

* expanded timeline/details
* safety report details
* places where the user needs precision

---

## 6. TRAVEL / TIMEZONE CHANGE HANDLING

Support dynamic timezone updates for the protected user.

Preferred approach:

* update user’s last-detected timezone from device/heartbeat/native context over time
* do not rely only on a one-time onboarding value

If the protected user changes timezone, future scheduling should follow the new timezone.

Keep v1 simple:

* automatic timezone update is fine
* do not build manual timezone preferences in this task

---

# IMPLEMENTATION GUIDANCE

## Backend

* keep canonical UTC timestamps
* store user timezone (IANA)
* check-in worker should calculate due times using the protected user’s timezone

## Frontend

* create a shared date/time formatting utility
* watcher view formats UTC → watcher local
* if user timezone differs, details can show:

  * watcher time primary
  * user local place/time secondary

---

# REQUIRED OUTPUT

After completion, report:

1. Where user timezone is stored
2. How timezone is detected/updated
3. How check-in scheduling now respects user timezone
4. How watcher-facing formatting works
5. Where dual-time appears
6. Any platform limitations found

---

# IMPORTANT SCOPE LIMITS

Do NOT build:

* manual timezone preference UI
* timezone settings page
* historical timezone correction tools

Keep this focused on clarity + scheduling correctness.

---

Goal:
Make cross-timezone families feel informed, not confused.
