 To Replit Agent:

  Before the final readiness checklist, we need a watcher/emergency-contact link audit. Discussion only first. Do not write code
  yet.

  Context:
  StillHere sends links to watchers / emergency contacts who may not want to download the app first. These links are important.
  They must work, show the right information, use safe wording, and expire appropriately.

  Founder requirement:
  No public watcher/emergency/contact link should last longer than 24 hours.

  Research context:
  - Google Maps public location-sharing links for people without a Google account can share real-time location for up to 24 hours.
  - Life360 Circle invite codes expire after 72 hours, but those are app-join invites, not incident/emergency access links.
  - WhatsApp live location is shorter: 15 minutes, 1 hour, or 8 hours.
  - Apple Find My supports 1 hour, until end of day, or indefinitely, but only inside trusted Apple account sharing, not anonymous
  web links.

  Recommendation direction:
  For StillHere, 24 hours max is the right ceiling for public web links. It is long enough for a real safety incident or emergency
  contact follow-up, but short enough to reduce privacy risk if a link is forwarded, screenshotted, indexed, or leaked.

  Please audit every public link StillHere sends to watchers, emergency contacts, family members, or responders who may not have
  the app installed.

  Audit scope:
  1. SMS links
  2. Email links
  3. Push/deep links that fall back to web
  4. Contact responder links
  5. Emergency incident links
  6. Safety Circle invite links
  7. Live location viewer links
  8. Drill/test links
  9. Report links, if any are public
  10. Any /e/:token, /emergency/:token, /contact, /live-location, /report, /watcher, /guardian, or similar tokenized route

  For each link type, report:
  - where it is generated, file/line
  - route/path format
  - token source/table/column
  - who receives it
  - what information the page shows
  - whether the recipient needs login or app install
  - current expiry behavior
  - whether the token is one-time, reusable, revocable, or tied to incident status
  - whether it is blocked from indexing via robots/noindex
  - whether it includes location, phone, name, heart rate, incident timeline, check-in status, or contact details
  - current wording shown on the page
  - current wording in the SMS/email that contains the link
  - whether it should expire at 24 hours, shorter than 24 hours, or immediately when incident resolves

  Proposed policy to evaluate:
  A. Emergency/SOS/contact responder links:
  Expire at the earlier of:
  - 24 hours after creation
  - incident resolved/closed
  - user cancels alert
  - token manually revoked

  B. Missed check-in links:
  Expire at the earlier of:
  - 24 hours after creation
  - check-in/incident resolved
  - token manually revoked

  C. Live location watcher links:
  Expire at the earlier of:
  - 24 hours after creation
  - live sharing/session stopped
  - incident resolved if incident-scoped
  - token manually revoked

  D. Safety Circle invite links:
  These can be different from emergency links. Propose either:
  - 24 hours for privacy consistency, or
  - 72 hours if the current UX depends on slower invite acceptance.
  Please recommend which is better for StillHere and explain tradeoff.

  E. Drill/test links:
  Expire at the earlier of:
  - 24 hours after creation
  - drill completed/cancelled

  F. Report links:
  If public/tokenized, expire within 24 hours.
  If authenticated-only, no public token expiry needed.

  Security/privacy expectations:
  - No public token route should be indexable.
  - Token should not expose more data than necessary.
  - Expired links should show a helpful page:
    “This safety link has expired. For privacy, StillHere links are only available for a limited time. If you are worried about
  someone’s immediate safety, contact them directly or call local emergency services.”
  - Resolved incident links should show:
    “This alert has been resolved.”
    Do not keep showing live location after resolution.
  - Drill links should clearly say it was a drill/test.
  - Pages must say StillHere is not an emergency response service where appropriate.
  - Keep language urgent but factual. Do not weaken real alerts into generic text.

  Return:
  1. Full link inventory table.
  2. Current expiry gaps.
  3. Recommended expiry policy per link type.
  4. Any HIGH-risk link that currently lasts forever or exposes location after resolution.
  5. Exact wording changes recommended for SMS/email/page states.
  6. Proposed implementation plan, but do not code yet.
  7. Test plan for link expiry, resolved incidents, revoked links, noindex, and mobile rendering.

  Do not start implementation until Codex/founder approves the policy and exact scope.
