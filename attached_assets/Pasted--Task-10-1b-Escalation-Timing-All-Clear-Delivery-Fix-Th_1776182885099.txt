🔴 Task 10.1b — Escalation Timing + All-Clear Delivery Fix

This is now the top priority.

Live testing showed two real failures:

1. SMS and call fired at the same time (1:56 AM)
2. Emergency contact did not receive the all-clear SMS after successful check-in resolution

Task 10.2 Safety Report is approved separately.
But escalation is NOT cleared yet.

---

# 🎯 OBJECTIVE

Make escalation:

* sequential
* calm
* predictable
* fully reliable

No simultaneous steps.
No silent all-clear failures.

---

# 1. PERSISTED ESCALATION STATE MACHINE

Add explicit persisted timing fields so the worker cannot fire multiple escalation steps in one tick.

Required fields (or equivalent):

* `push_sent_at`
* `sms_sent_at`
* `call_sent_at`
* `last_escalation_step`
* `next_escalation_at`

---

# 2. ENFORCE HARD GAPS BETWEEN STEPS

Required behavior:

### Step sequence

1. Push
2. wait configured grace period
3. SMS
4. wait configured grace period
5. Call

### Rule

If:

* `last_escalation_step = sms`
* and `now < sms_sent_at + gracePeriod`

Then:

* EXIT
* do NOT place call

No two escalation steps may fire in the same worker execution.

---

# 3. ATOMIC STEP ADVANCE

When a step is sent successfully:

* update the relevant `*_sent_at`
* update `last_escalation_step`
* update `next_escalation_at`

This must happen safely so state cannot drift.

At minimum, the code must ensure we never record a step as sent without tracking the next allowed escalation moment.

---
